# Changelog

All notable changes to Zest. Versions before v3.0 were not tracked in this file.

## v3.1.2

- The dropdown closes on the first click outside it (the desktop, another app's window, another menu bar icon) and on Escape. It used to stay open until you clicked the Zest icon again, or clicked inside it first: the popover only closes itself on an outside click while Zest is the active app, and a menu bar app is not active when its dropdown opens (the same since v3.0). Zest now becomes active as the dropdown opens and watches for outside clicks only while it is open; when it closes with no other Zest window open, the focus goes back to the app that had it.
- The close button on an alert pill closes that pill. It used to close the app's key window, or the first visible window, so with the Command Center open, or two pills on screen, it closed the wrong window and left the pill (2026-09-02 audit Z-B10).
- Command Center > Alerts: a run of the same alert is one row with its count and its first and latest times, so a charger plugged in fifty times no longer pushes every other alert out of the list. A different alert in between starts a new row, so the order of events stays. An existing history file is folded the same way when Zest starts; on the developer's Mac, 50 rows (49 of them "Charger connected") became 3.
- The months-to-80-percent projection in Battery Health fits a line through every daily capacity sample (least squares) instead of drawing it through the first and last samples only, where one odd reading at either end set the whole projection (audit Z-B11). With a flat history, as on most Macs in their first months, it still shows no date.
- A second copy of Zest exits even when the lock file in Application Support cannot be opened: it then checks for another running Zest by bundle identifier. Before, an unopenable lock file let every copy run, each with its own menu bar icon (audit Z-B13).

## v3.1.1

- From the first time the dropdown was opened until Zest quit, Zest used about 30 percent CPU and kept WindowServer busy, and the menu bar icon was reported flickering. The dropdown's SwiftUI view stayed alive after the popover closed, and its power-flow animation repeats forever, so the closed popover was laid out and rendered on every display frame. The dropdown is now built when it opens and released when it closes. Measured on the developer's Mac over 20 s after one open and close: Zest 30.2 percent CPU before, 0.3 percent after. A closed Command Center window keeps its place; its power-flow dots pause while it is closed. Details: `docs/2026-10-29-render-loop-and-battery-keys.md`.
- The menu bar icon is redrawn only when something it shows changes (the percent, power and charging state, the time text when shown, the style options, the Claude readout), and change signals are coalesced to at most four checks a second. Before, every state change in the app (an energy sample, a device scan, a new voltage reading) drew and set a new image: about seven a minute at rest and nineteen in the first second, each one re-rendered by the menu bar on every display. The renderer now reads only the values the check compares, so a visible change cannot be skipped; the old and new renderers draw identical pixels for 5,760 input combinations.
- The open dropdown no longer collapses and regrows every 1.2 s. The power-flow dots were driven by an endless `withAnimation` started in `onAppear`, and that animation also caught the dropdown's first layout, so the whole card was redrawn from the top in a loop (present since v3.0). It never moved the dots either: its start and end values put every dot in the same place. The dots now take their position from the clock (`TimelineView`, 30 frames a second) and really travel along the links; nothing in the dropdown animates layout.
- The dropdown fits its content up to 640 points and scrolls beyond that. It used to open at a fixed 320 x 320, because the hosting controller never reported a preferred size to the popover, so everything below the power flow needed scrolling.
- Battery Health on macOS 27: Temp, Design and Full showed "--". macOS 27 moved `DesignCapacity` into the `BatteryData` sub-dictionary of the AppleSmartBattery registry entry, replaced `AppleRawMaxCapacity` with `BatteryData.FullChargeCapacity`, and dropped `Temperature` with no live replacement in the registry. Zest reads the new keys as a fallback (the old top-level keys still come first, for older macOS) and takes the temperature from the battery's SMC sensors (`TB0T`, `TB1T`, `TB2T`; read-only, as the logged-in user, no helper or root). If no sensor answers, the tile says "Not available on this macOS" instead of "--". The event log's `battery_temp` events, the daily health history, the digest and the export get the temperature back too; all four had been empty on macOS 27. Maximum Capacity is unchanged: it still comes from `system_profiler`, which is the figure System Settings shows.

## v3.1

- Release builds carry no build paths. The v3.0 binary held 76 absolute paths with the builder's home folder in its debug symbol table. `build.sh release` now strips debug symbols (`strip -S`; function names stay for crash reports) and runs `scripts/check-bundle-paths.sh`, which greps the raw bytes of every file in the signed bundle for `/Users/` and for the build user's name as a whole folder name (`/<name>/`) and fails the build on any hit, or with exit 2 when a file cannot be read. `strings -a | grep /Users/` is not a valid check: on macOS 27 it printed 0 for a binary holding 87 such paths. `scripts/test-bundle-paths.sh` (run by CI) checks the check on planted fixtures. `notarize.sh` runs the same check before it submits anything.
- Homebrew: `brew install --cask shashankkarpal/tap/zest`. `brew uninstall --cask zest` also boots out and removes the `com.zest.app` LaunchAgent, so a KeepAlive job is never left relaunching a deleted app.
- Root helper trimmed to what the app sends. `zest-smc` loses `limit-set` (the SMC charge write; charge care stays with macOS), `limit-get`, `read`, `size` and the whole SMC client, and `lowpowermode` accepts exactly `0` or `1`. `probe` now answers with a helper interface number; a helper installed before v3.1 answers without one, and the Command Center's Charge Limit card then asks for a re-install, because that helper's grant allowed any arguments. The sudoers grant written by `install-helper.sh` names the exact argument vectors (`probe`, `lowpowermode 0`, `lowpowermode 1`, and the pinned `powermetrics` line) instead of the bare helper path, which allowed any arguments as root. Re-run `sudo bash zest-smc/install-helper.sh` to replace an older grant. `install-helper.sh --print-sudoers <user>` prints the grant without root, and `zest-smc/test-helper.sh` (run by CI) checks the helper, the grant, and that every `sudo -n` call in `Sources/` is covered by it.
- Command Center > Alerts: the last 50 alerts Zest raised, newest first, with the ones quiet hours silenced marked as such, plus Clear. Persisted in `alerts-history.json` beside the config.
- Energy history rolls hourly buckets older than seven days into UTC daily buckets (sums and sample counts add, so the 7d and 30d averages are unchanged; the 24 h sparkline keeps hourly resolution). The owner's file went from 4.6 MB (659 hourly buckets) to 1.6 MB (167 hourly plus 23 daily) with every sample accounted for.
- Battery health shows the system thermal pressure (Nominal, Fair, Serious, Critical) from `ProcessInfo.thermalState`, pushed on change; the same signal the event log records as `thermal_state`.
- SIGTERM (launchctl bootout, logout, shutdown) now runs the normal quit path, so the energy history tail is flushed and the `zest_stop` event is written; before, the process died without `applicationWillTerminate`.
- `bash build.sh [release|debug] install` copies the finished bundle to `~/Applications/Zest.app` (or `ZEST_INSTALL_DIR`) with an atomic swap. Until now the only bundle was the in-tree build product, and `build.sh` begins by deleting it, so every rebuild removed the very file the LaunchAgent was running. `scripts/install-launchagent.sh` now prefers the installed copy, validates the plist, and reloads with bootout then bootstrap (the only sequence launchd accepts after the program changes).
- History keys are UTC (2026-09-02 audit Z-B9). Energy buckets (`yyyy-MM-dd-HH`) and daily health samples (`yyyy-MM-dd`) used to be keyed in the Mac's current zone and locale, so a timezone change would have shifted every bucket. On first launch after this update the energy history is re-keyed once from the Mac's current zone to UTC (`energy/meta.json` gains `keyZone: UTC`; buckets that land on the same UTC hour are merged with their sample counts, so averages stay exact) and health samples get their day re-derived from their stored timestamp.
- Event log for local tools (Settings > General > Event log). Optional folder; when set, Zest appends one JSON line per event to `zest-events.jsonl`: `plugged_in`, `unplugged`, `fully_charged`, `charge_cycle`, `battery_temp` (normal / warm at 35 C / hot at 40 C with 2 C hysteresis), `low_power_mode`, `thermal_state`, `zest_start`, `zest_stop`. ISO-8601 UTC `ts`, `source`, `host`, `version`. Rate limited to one line per event type per minute (lifecycle exempt), rotated at 1 MB with one previous generation kept. No network, no daemon, off by default.
- Energy pass (2026-09-02 audit Z-B1, Z-B2, Z-B4, Z-B7, Z-B8). Panel scripts now run only while something shows their output (the Command Center window, or the menu bar readout for the account panels) and never overlap themselves; before, all four ran from launch forever, and a 5 s System Vitals script that took longer than 5 s ran 98 percent of the time. `system_profiler SPPowerDataType` moved off the main thread (it used to block the UI for 2 to 12 s inside every hourly refresh); cycle count is read from the IORegistry on every refresh. One shared `system_profiler SPBluetoothDataType` snapshot per 30 s serves both the Devices list and Presence instead of two runs. Low Power Mode state comes from `ProcessInfo` (no shell; the old `pmset -g | grep` ran on the main thread inside a SwiftUI body on every redraw, and on current macOS always read Off). The helper probe at launch runs off the main thread. `EnergySampler` runs on one serial queue and skips a tick instead of overlapping a slow powermetrics run; it also stops rewriting the multi-megabyte energy history on every 12 s tick (now every 5 minutes plus on quit) and stops allocating a DateFormatter per bucket per pass, which turned out to be most of Zest's own idle CPU. `Shell.run` waits on the child instead of polling every 20 ms. Measured on the running app over two 600 s windows: Zest CPU time 25.9 s before, 1.9 s after (about 4.3 percent of a core down to 0.3), panel-script spawns 14,235 sample hits before, 0 after, Bluetooth profiler runs roughly halved.
- First unit tests: `swift test` runs 25 XCTest cases over config decoding (tolerant decode, panel gate default off, round trip), panel gating (inert runner, missing script never spawns, four personal sections), battery snapshot math, health projection, and the JDict accessor. `BatteryHistory.projection` became a pure static function so it can be tested without touching disk. New `build` GitHub Actions workflow runs the tests and a release `build.sh` on a macOS runner, so a broken build no longer waits for someone's local build to notice.
- Widget panels are gated behind a `panelsRoot` setting (Settings > General > Widget panels). With no folder chosen, which is every fresh install, the four personal Command Center sections (Account 1, Account 2, System Vitals, Claude Code) are hidden, no panel script is ever spawned, and the menu bar readout picker that depends on them is hidden. Before this, the public build showed the sections empty and ran `/bin/bash` against hard-coded `~/Projects/zest/panels/*.sh` paths every 5 to 30 seconds (2026-09-02 audit Z-B3, Z-A8). The runner also stays silent when a chosen folder goes missing instead of failing four times a cycle.
- The privileged helper is looked up only at its installed path `/usr/local/libexec/zest/zest-smc`; the old `~/Projects/zest/zest-smc/zest-smc` fallback could never have passed the sudoers grant.
- In-app privacy text no longer describes a VPN egress check that belongs to one user's own panel script.
- README: merged the two conflicting Install sections; the notarized download is primary, build-from-source is the alternative.
- build.sh: no personal signing identity as default; `ZEST_SIGN_IDENTITY` is required for Developer ID signing (the default was still present until 2026-09-02; now actually removed).
- Security (2026-09-02 fleet audit): the sudoers grant for `powermetrics` is pinned to the exact argument vector Zest runs instead of allowing any arguments (an unrestricted grant let any user process create or truncate arbitrary files as root via `-o`). `install-helper.sh` refuses to install when `/usr/local` or `/usr/local/libexec` is not root-owned (sudoers path-hijack). `trigger-install.sh` logs to a `mktemp` path.
- New `zest-smc/uninstall-helper.sh` and `scripts/uninstall-launchagent.sh`; README gained an Uninstall section and an accurate description of the helper (the app never prompted for a password; the README said it did).
- `install-launchagent.sh` resolves the app path from the repo location (or `ZEST_APP`) instead of a hard-coded `~/Projects/zest`.
- Config is written atomically, and an undecodable `config.json` is preserved as `config.json.bad` instead of being overwritten with defaults.
- `exportJSON` no longer silently writes nothing when a health value is missing (optionals are encoded as null).
- The Accessibility notification dismisser matches exact macOS battery phrases only; it used to close any banner containing "charge".
- BLE cache path fixed (`~/../tmp` had resolved to `/Users/tmp`); the reader now trusts only a regular file owned by the current user.

## v3.0

- Signed and notarized Developer ID release: download from Releases, no Xcode required.
- Privileged helper (`zest-smc`) for Low Power Mode toggle and true per-app powermetrics energy.
- Ecosystem battery view, health history with capacity trendline, energy grading, Ubersicht panel embedding, local LM Studio digest.
